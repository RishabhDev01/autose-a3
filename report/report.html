1. Architecture

A Python state machine, the orchestrator, runs the six stages of the workflow. It does not call a language model itself. Three agents do the model work. The planner writes the specification and the design (stages 1 and 2). The builder writes the code and the tests (stages 3 and 4). The reviewer checks the pull request (stage 6), and it runs in its own job. Two helpers make single calls. A prompt-injection classifier screens the issue text, and a judge checks that every acceptance criterion can be tested. After each stage, code decides whether the stage passed (ADR-002, ADR-007). The stages pass work to each other as files on the issue branch, under .autose/issue-N/ (ADR-003, ADR-004). The workflow never merges a pull request.

How the reviewer is kept from simply agreeing with the implementer

We use five measures (ADR-008, ADR-021, ADR-026). (1) It runs in a separate job on a fresh checkout of the pull request, with a read-only token: it can read the code and run the tests, but it cannot push or comment. (2) It receives only the issue and the diff. The .autose/ folder (specification, design, test report) is deleted before it starts, and its tools refuse to read .autose/, autose/ and .github/, so it never sees the implementer's reasoning or our own prompts. (3) It uses its own prompt and a different model series from the builder (Gemini 4 Hydrogen against Gemini 3.8 Flash). (4) Code checks its verdict: the reviewer must have run the full test suite, must list each requirement with evidence and at least two risks, and an approval that still lists an unmet requirement or a defect is rejected. A verdict that fails these checks three times is recorded as "changes", never as an approval. (5) We measured it: on five seeded pull requests whose tests all pass, it rejected all four buggy ones and approved the correct one, and it also rejected the builder's gamed PR 26 that every automatic check had passed (Section 4). Requested changes name the stage to return to (design or implementation); the post job then offers /autose round 2 <stage>, at most two rounds, and a person decides whether to start it.

Decision 1: the builder edits code chosen for it (ADR-016)

Our first builder was an agent with file tools. In run 10 it used all 40 turns without applying a single edit: thirteen file reads had bad arguments and nine edits did not match the file. Run 12 repeated the pattern and used 179k tokens. We changed the design so that the orchestrator finds the relevant definitions with Python's ast module and sends them, with their helper functions and the project's invariants, in one request. The builder replies with complete replacement definitions, and the orchestrator applies them by name. Successful builds after this change used one or two calls and 3k to 8k tokens. The cost is that the builder sees only what it is given. Runs 22 and 25, and the import problem found in E2, all came from that limit.

Decision 2: an independent reviewer behind code checks (ADR-008, ADR-026)

Run 27 shows why both are needed. Issue 7 asks for behaviour that an existing test forbids. After five failed attempts, the builder made Table.search() inspect the call stack and run the old code only when called from that test. All automatic checks passed, including 231 tests and CI. The reviewer, which saw only the issue and the diff, identified the stack inspection and requested changes. We then added a scan that rejects such code, and a rule that stops a run when only existing tests keep failing after a redesign. With these rules, run 27 would have stopped at attempt 5.

Decision 3: planning around provider limits (ADR-013, ADR-015, ADR-019)

The free Groq key allows 8k tokens per minute and 200k per day for each model. Run 2 failed on request size, run 11 waited 2.5 hours for quota and was cancelled, and none of the pipeline runs up to run 16 produced a pull request. Moving the planner and builder to a paid Gemini tier reduced a build from hours to 2.5 minutes (run 17), for about US$2 in total. We now treat rate limits as a design constraint from the start.

3. Decision experiments

Each experiment changed one input and compared the results with ground truth that the agents could not see. The details are in experiment/variants.md.

E1: reviewer model (ADR-008, ADR-021)

Five seeded pull requests (four with a known bug, one correct, all with passing tests) were reviewed twice with the same prompt and workflow. Only the reviewer model changed. We also asked the builder's own model to review its gamed PR 26.

Figure 3. E1. Black: Gemini 4 Hydrogen (default). White: Gemini 3.8 Flash, the builder's model.

Both models caught all four bugs for the right reason, raised no false alarm, and rejected PR 26. The result does not support the claim that a different model is needed for accuracy. We kept Hydrogen because it reached the same verdicts with 3.4 times fewer calls at about half the cost, and we weakened the independence argument in ADR-021.

E2: hand-off to the builder (ADR-003)

Twenty builder-only runs: five issues, two hand-offs (full specification and design, or a fixed five-line summary) and two repetitions. The specification, design, code shown and checks were fixed. Hidden tests were run with Python 3.12.

Figure 4. E2. Black: full hand-off (default). White: five-line summary. The single difference is issue 5.

The summary saved about 5 % of tokens, because the code shown to the builder takes up most of each request. It lost one run (issue 5, repetition 2), and issue 7 failed in the same way under both hand-offs. We kept the full hand-off (ADR-028). The experiment also showed that the builder cannot add an import: every issue 5 first attempt used Any without importing it.

Both experiments are small (six pull requests in E1, two runs per cell in E2), so we read them as directions rather than significant effects.

What the reviewer caught. The reviewer caught the test gaming in PR 26, which every automatic check had passed. It also caught all four seeded bugs, each with the right line and cause: a swallowed KeyError, a missing conversion in update, None returned instead of skipping, and a shared mutable default argument. It approved the correct seeded PR.

Where it was wrong or weak. We saw no wrong verdict in sixteen reviews, but there were weaknesses. On PR 26, Hydrogen suggested changing the old test, which is a product decision the reviewer should have left to the maintainer. The Groq-hosted reviewer in run 17 ended without running the full test suite, so its verdict was rejected. A reviewer that reads only code cannot tell that a design was wrong if the code follows it. In runs 21 and 22 the tests caught the wrong designs before review.

5. Hindsight

If we started again, the first decision we would change is ADR-005, building the builder as a tool-calling agent on a free, rate-limited provider. We chose it because it is the usual pattern. With an 8k tokens-per-minute limit, each turn resent a growing history, so a confused model used up both its turns and the quota. The nine pipeline runs from run 2 to run 16 produced no pull request. We would start with the select, patch and validate builder and the failure summary, and choose the provider by its rate limits. We would keep the independent reviewer, the code checks and the file hand-offs, because they gave reliable evidence even when runs failed. We also learned to check results with the same Python version as CI. Our first local check used Python 3.14 and scored a branch that does not import on Python 3.12 as passing. We repeated every hidden-test check with 3.12, and no earlier result changed.

6. Limitations and threats to validity

  • Tuning on the test issues. ADR-013 to ADR-026 were each written after a failure on issues 3 to 7, and the same issues were then re-run. The success rate is therefore likely to be higher than on new issues. Issue 5, which passed on its first full run, is the cleanest result.
  • Human help. A person clarified an invariant in ARCHITECTURE.md after two wrong designs, so issue 4 was not solved by the agents alone. People also restarted runs at the design stage and make every merge decision.
  • Small samples. There are five issues, six pull requests in E1 and two runs per cell in E2. Each pipeline issue reached success once and was not repeated, although model outputs vary (in E2, issue 5 passed in three of four runs).
  • Our own ground truth. The hidden tests encode one reading of the vague issue. The seeded bugs are single bugs visible in the diff, written by the same team that built the reviewer, so harder bugs spread over several files were not tested.
  • Limited independence. The reviewer and the builder are both Gemini models, although from different series. E1 found equal accuracy, but models from one vendor may share blind spots that our tests did not reveal.
  • Incomplete measurement. Token totals are missing for three runs that stopped before reporting. The prompt-injection guard was never tested against a real attack. Review round 2 (returning requested changes to an earlier stage) is implemented and was triggered once (run 28), but that run was blocked by the gate, so no completed round 2 exists.

The workflow pushes and comments only in our fork and never merges. API keys are kept in repository secrets. A spending limit was set before paid use. All runs, pull requests and reviews are real and linked in results/runs.md.
