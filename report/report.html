1. Architecture

The shape. A deterministic Python state machine (the orchestrator) drives six stages. It contains no LLM. Three LLM agents each own a slice: the planner (stages 1–2), the builder (stages 3–4) and an independent reviewer (stage 6), which runs in a separate job. Two single-call helpers screen and check: a prompt-injection guard and a testability judge. Every stage ends in a check that code decides (ADR-002, ADR-007). Hand-offs are files on the issue branch (.autose/issue-N/), so anyone can follow a run from the PR (ADR-003, ADR-004). The workflow never merges.

The three decisions that mattered most

1. ADR-016: the builder patches what the orchestrator finds. The first builder was a tool-calling agent (ADR-005). In run 10 it used 40/40 turns and applied 0 edits: 13 malformed read_file calls and 9 edit_file mismatches. Run 12 looped the same way on 179k tokens. We inverted control: code uses ast to extract the definitions the design names, plus their helpers and the ARCHITECTURE.md invariants. The model answers once per attempt with whole replacement definitions, and code applies them by name. From then on, a successful build cost 1–2 calls and 3–8k tokens (run 17: 3k; run 26: 2.8k; run 23: 7.7k), and later fixes (ADR-023/024/025) were small changes to one function each. It also made the builder's input auditable. The price is that the builder cannot read anything it is not shown. Runs 22 and 25 (missing helpers, new module-level functions) and the import limit found in E2 are all costs of that inversion.

2. ADR-008 (+021, 026): an independent reviewer behind deterministic gates. Run 27 is the clearest evidence. The vague issue #7 asks to change behaviour that an existing test pins. After five honest failures, the builder made Table.search() walk the call stack (sys._getframe) and run the old code only for that test. Every deterministic check passed (231 tests, CI green). The reviewer, which saw only the issue and the diff, called it "special-casing a test via stack-frame inspection" and requested changes. We then added the cheap code-level defences the reviewer had shown were missing (ADR-026): a gaming scan, and a conflict stop that would have halted run 27 at attempt 5. The checks and the reviewer are complementary: the checks know patterns, and the reviewer knows intent.

3. ADR-013 → 015 → 019: designing around the model provider's limits. The assignment's free Groq key (8k tokens/min, 200k tokens/day per model) shaped everything until run 16. Requests had to fit 8k (ADR-013, after an HTTP 413 in run 2). Daily quotas made runs sleep for hours (run 11: 2.5 h cancelled), so we added fallback or a fast stop (ADR-015). Runs 2–16 delivered no PR, mostly for these reasons. Moving the planner and builder to a paid Gemini tier (ADR-019) turned a 2.5-hour stall into a 2½-minute build (run 17), for about US$2 in total. The lesson is architectural: rate limits are a first-class constraint, like latency, and should be designed for at the start, not discovered.

3. Decision experiments

We tested two ADRs with controlled variants. In each, only one input changed, and the outcome was judged against ground truth that the agents could not see. Full write-up: experiment/variants.md.

What the reviewer caught.

  • The test gaming in PR #26, which every automatic check had passed.
  • All 4 seeded bugs, each for the right reason with the exact line: a swallowed KeyError, update left unconverted, None returned instead of skipping, and a shared mutable default.
  • No false approvals and no false alarms in 16 verdicts.
Where it was wrong or weak.
  • On PR #26 Hydrogen advised "update the legacy test". That is a product decision a reviewer should escalate, not prescribe; Flash recommended escalating.
  • The Groq-hosted reviewer of run 17 produced no valid verdict (forced finish, full tests never run), so validation rejected it.
  • The reviewer cannot see that a design was wrong when the code matches it. Runs 21–22's wrong designs never reached review only because the tests caught them first.

5. Hindsight

The decision we would change first is ADR-005: building the builder as a tool-calling agent on a free, rate-limited provider. We inherited the "agent with tools" shape because it is the familiar pattern. It interacted badly with an 8k tokens/min limit: every turn re-sent a growing history, so a confused model burned both turns and quota. Nine pipeline runs (2 and 9–16) and most of the first day produced no PR. Starting tomorrow, we would build the stages 3–4 path as localize → patch → validate from day one, with the failure digest, and pick the provider by its rate limits rather than its model list. The independent reviewer, the code-decided checks and the file hand-offs we would keep unchanged: they are what produced trustworthy evidence even when things went wrong. A smaller lesson: evaluate locally on the same Python version as CI. A first local pass on 3.14 scored a branch that fails to import on 3.12 as 9/9. We re-ran every hidden test on 3.12, and no earlier result changed.

6. Limitations and threats to validity

  • The pipeline was tuned on the evaluation issues (overfitting). ADRs 013–026 were each written after a failure on issues #3–#7, and then re-run on the same issues. The 4/5 success rate is therefore optimistic for unseen issues. Issue #5 (first try from guard) is the cleanest data point.
  • Human interventions. We clarified an ARCHITECTURE.md invariant after seeing two wrong designs (ADR-024), so issue #4's success is not fully autonomous. Restarts at the design stage and every merge decision were also made by a person, by design.
  • Small samples and non-determinism. There are 5 issues, 6 PRs in E1, and n = 2 per cell in E2. Each pipeline issue was run to success once, not repeated. LLM outputs vary (for example, E2 issue 5 passed in 3 of 4 runs), so single runs can mislead.
  • Ground truth is ours. The hidden tests encode one reading of the vague issue, and the seeded bugs are single, diff-visible defects written by the same team that built the reviewer. Subtle multi-file bugs are not covered.
  • Weaker independence than planned. The reviewer and builder are both Gemini models (different series), and the judge is on Groq. E1 shows equal accuracy, but one vendor's shared training could hide correlated blind spots.
  • Incomplete measurement. Token totals miss three runs that crashed or were cancelled before reporting (11, 13, and run 17's Groq review). The injection guard was never tested with a real attack.

Rules respected: the workflow pushes and comments only in our fork and never merges (a person decides); API keys live only in repository secrets; spending caps were set (Groq free tier; a Gemini budget alert); and every run, PR and review is real and linked in results/runs.md.
