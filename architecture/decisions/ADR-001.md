# ADR-001: Split the work across three agents plus deterministic code

## Status
Accepted (2026-11-21)

## Context
There are six fixed stages. The options range from one agent doing everything to one agent per stage. We use the Groq free tier, which has tight per-minute and per-day token limits. Every agent's context costs tokens, and re-reading the repo costs tokens again.

Stages 1 and 2 need the same context: the issue, ARCHITECTURE.md and a skim of the code. Stages 3 and 4 need the same context too: the design, the files being edited, and test output. When tests fail, the fix needs to remember what was just changed. Stage 5 needs no judgement at all. Stage 6 must not share context with anyone.

## Decision
- **Planner agent**: stages 1 and 2.
- **Builder agent**: stages 3 and 4, in one conversation, so a retry after a test failure keeps its context.
- **Release**: a plain script with no LLM.
- **Reviewer agent**: stage 6, run in a separate job.

That makes three LLM agents. There is also a small LLM judge, which is a single call, not an agent.

## Options considered
- **One agent for everything.** Rejected. It would review its own work, and its context grows past Groq's TPM limit.
- **One agent per stage (6).** Rejected. Each would start cold and re-read the repo, wasting tokens. The tester would also not know what the implementer changed.
- **Three agents plus code (chosen).**

## Consequences
- Fewer tokens used, and the retry loop stays inside one conversation.
- The builder writes both the code and the tests, so it could write weak tests that pass. Two things mitigate this. The orchestrator requires each AC-n to have a test. The independent reviewer and the hidden tests then check the result.
- Tested in experiment E2 (see ADR-003).
