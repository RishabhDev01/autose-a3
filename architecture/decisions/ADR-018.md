# ADR-018: Quota stops are pauses, and a schedule resumes them

## Status
**Rejected** (2026-11-22). It was proposed after run 14 and implemented in fork [PR #14](https://github.com/RishabhDev01/tinydb/pull/14), which was closed without merging.

The maintainer chose to keep every run started by a human: no scheduled runs on the fork. A quota stop therefore stays a stop with `resume_at` (ADR-015/016), and the maintainer resumes it with `/autose` once the quota has refilled.

## Context
Run [44973325961](https://github.com/RishabhDev01/tinydb/actions/runs/44973325961) did exactly what ADR-015–017 intended:
- it synced the branch with master;
- spec passed;
- design stopped within seconds when both gpt-oss models hit their daily quota (`Used 199449/200000` and `195763/200000`);
- it saved `resume_at: design`.

To the maintainer, though, it looked like **the same failure again**: a red ❌ and an "AutoSE stopped" comment. Someone also had to come back after the quota refilled (about 8k tokens per hour per model) and comment `/autose` again.

On the free tier, a quota stop is a **normal, expected state**, not an error. Over five issues and two experiments it will happen many times.

## Decision
1. **Pause, don't fail.** On `QuotaExhausted`, the orchestrator:
   - sets `status: paused`, `resume_at: <stage>` and `paused_at`, and pushes the state;
   - comments **"AutoSE paused … Nothing failed"**, saying how to resume;
   - exits 0.

   The run shows green, and review and post are skipped because the status is not `released`. Real failures still exit 1 with "AutoSE stopped".
2. **Resume on a schedule.** `autose.yml` gains `schedule: cron "17 */3 * * *"`. On a tick, the gate:
   - lists `autose/issue-N` branches and reads each branch's `state.json`;
   - picks the **longest-paused** issue that has been paused for at least 60 minutes, so the quota has refilled a little (older `stopped` + `resume_at` states count too);
   - resumes it **in its round** at the saved stage;
   - **skips the tick** if another AutoSE run is in progress, because that run is using the same quota;
   - resumes **one issue per tick**.
3. **Authorization is unchanged** (ADR-010). Only issues a maintainer already started with the label or `/autose` have a branch, so a tick never starts new work. It only continues what a human already approved. The gate job gets `actions: read` to check for running runs, and nothing else.

## Options considered
- **Keep exiting 1 and rely on the comment text.** Rejected: the maintainer reads the red ❌, not the text, as run 14 showed.
- **Have the paused run re-dispatch itself after a delay.** Rejected: there is no delayed `workflow_dispatch`, and a sleeping job wastes runner time and can hit the job timeout (run 11).
- **Resume every paused issue on each tick.** Rejected: they would compete for the same quota and pause each other halfway through a stage.
- **Tick hourly.** Rejected: about 8k tokens of refill per model per hour is less than one design stage, so most ticks would pause again at once. Three hours gives about 25k per model.

## Consequences
- The maintainer can queue several issues; they finish over the day without anyone watching.
- A tick that comes too early pauses again cheaply: the first refused call stops it, and `paused_at` moves on.
- **Edge case:** a manual `/autose` on the same issue during a scheduled resume would run in a different concurrency group. The gate's in-progress check makes this unlikely but not impossible.
- GitHub runs scheduled workflows on a best-effort basis, so ticks can be late. Correctness does not depend on their timing.
- **Tested** with a stubbed GitHub API:
  - the gate picks #3 (paused 01:53) before #4 (paused 03:00) and keeps #4's round 2;
  - it ignores released and normally-stopped issues;
  - it waits out the 60-minute minimum, skips while another run is in progress, and still rejects bots;
  - a `QuotaExhausted` in design gives exit 0, `status: paused`, `resume_at: design`, a push, and the "paused" comment, with no STOPPED text added to any artifact.
