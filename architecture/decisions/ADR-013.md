# ADR-013: Size every LLM request to Groq's free-tier per-minute token limit

## Status
Accepted (2026-11-22). Amends [ADR-003](ADR-003.md) (hand-off sizes) and [ADR-009](ADR-009.md) (budgets), based on a real run.

## Context: what the first real run showed
Run [44937234625](https://github.com/RishabhDev01/tinydb/actions/runs/44937234625) on issue #3 got through the gate, setup, the injection screen (score 0.0007) and the test baseline (227 passed). It then **stopped at stage 1** on the planner's 6th call:

> HTTP 413: Request too large for model `openai/gpt-oss-120b` … tokens per minute (TPM): Limit 8000, Requested 8033

On the free tier, `gpt-oss-120b` has an **8,000 TPM** limit. A single request is rejected outright if `prompt tokens + max_tokens` exceeds it. Our earlier settings came from ADR-003/009 and were guessed without data:
- `max_tokens=4096`, which Groq reserves up front, so half the limit was gone before any prompt;
- context compaction only above 24,000 characters (about 6,500 tokens);
- tool outputs of up to 12,000 characters;
- the design prompt carrying all of ARCHITECTURE.md (about 8k characters).

The stop itself worked as ADR-009 intended: the reason was written to `state.json` and `spec.md`, posted on the issue, and the branch was pushed.

## Decision
| Setting | Before | After | Reason |
|---|---|---|---|
| `max_tokens` per call | 4096 | **1800** | the reservation counts towards the 8k |
| Reasoning effort | default | **low** (gpt-oss), **none** (qwen) | hidden reasoning tokens use up `max_tokens`; dropped automatically if a model rejects the parameter |
| Context limit (characters) | 24k–30k | **15k–16k** (about 4.5k tokens) | prompt + tool schemas + 1.8k output < 8k |
| Compaction | stub out old tool outputs | + shorten old tool-call arguments (drafts, whole files), + truncate recent outputs to 1.5k; **arguments are now counted** in the size | the drafts passed to `finish` were invisible to the old size count |
| On HTTP 413 | stop the run | **compact to 65% and retry, up to 3 times** | one oversized turn should not kill the run |
| Tool output, `read_file` | 12k chars, 150 lines | 5k chars, 80 lines | |
| Design prompt | all of ARCHITECTURE.md | **§4–§5 only** (2.4k chars) + `read_file` for the rest | |
| Reviewer diff in prompt | 14k chars | 6k chars, then `read_file` | |
| Retries on 429 | 6 | 10 | at about 5k tokens per call, only about 1–2 calls fit per minute |
| Build / review timeout | 60 / 30 min | 150 / 60 min | the per-minute limit makes long runs inevitable |

## Options considered
- **A paid tier** (higher TPM). Rejected: the assignment constraint is the free key.
- **`gpt-oss-20b` for the builder** (smaller, maybe higher limits). Kept as a fallback through `BUILDER_MODEL`. Not chosen first, because tool-use quality matters more than speed.
- **Summarising the history with an LLM call.** Rejected: it costs tokens from the same budget. Deterministic truncation is free.

## Consequences
- Agents see less context per turn and must re-read files more often, so they take more turns and runs are slower.
- Spec and design must stay short. The output cap (1,800 tokens) bounds their size.
- **Threat to validity:** results reflect free-tier limits, not the models' full ability.
