# ADR-015: Daily quota, so fall back or stop; never sleep for long

## Status
Accepted (2026-11-22). Amends [ADR-009](ADR-009.md) (rate-limit handling) and [ADR-011](ADR-011.md) (models), based on run 11.

## Context: what run 11 showed
Run [44942070537](https://github.com/RishabhDev01/tinydb/actions/runs/44942070537) on issue #3 was the first with the tolerant tools (ADR-014). Its outcome:
- **Spec passed** in under a minute (4 ACs, judge passed on the first attempt).
- **Design passed, but took 87 minutes** (19:40 → 21:07 UTC).
- The **builder made 3 read-only turns in 80 minutes**. Then the job hit its **2h30m timeout** and was cancelled.

The step log shows why. On gpt-oss-120b, every call got a 429 with `retry-after` values of **423 s, 1017 s, 1243 s, 1391 s, 1579 s and 1659 s**. ADR-009's backoff honoured each one and slept.

A per-minute (TPM/RPM) limit never asks for more than about 60 s. Waits of 7–28 minutes mean the model's **daily token quota** was spent: runs 9 and 10 earlier that day used about 190k tokens on gpt-oss-120b, most of it the builder's 40 turns in run 10. ADR-009 treated every 429 the same way, so a spent quota turned into hours of sleeping, and the stop reason the issue got was just "timed out".

## Decision
- **Classify the 429** by its `retry-after`. If it is more than `AUTOSE_LONG_WAIT_S` (90 s), the model's quota is spent: mark the model exhausted for the rest of the run. Shorter waits are handled with the ADR-009 backoff as before.
- **Fall back** to another model with its own quota. `AUTOSE_FALLBACK` defaults to `openai/gpt-oss-120b>openai/gpt-oss-20b`, so the **planner and builder** fall back to gpt-oss-20b.
- **No fallback for the judge or reviewer** (qwen). Falling back to gpt-oss would put them on the same family as the planner and builder, which would break the independence ADR-008 relies on. They stop instead.
- **If nothing is left, stop immediately** with `QuotaExhausted`, naming the models and their retry times. The orchestrator's normal stop path posts this on the issue and writes it into `state.json`.
- **Record each fallback** in the token usage (`fallback_calls` per role), so `results.csv` shows which runs used the smaller model.
- **Log the 429 message** (first 220 characters), so the limit type is visible in the step log.

## Options considered
- **Keep sleeping, with a longer job timeout.** Rejected: GitHub caps a job at 6 h, a run would take hours, and runs for the other issues queue behind it.
- **Use gpt-oss-20b for everything.** Rejected: a weaker builder. We keep 120b as the first choice and record when the fallback was used.
- **Fall back to qwen for the planner/builder.** Rejected: qwen is the judge and reviewer, and sharing the model would weaken independence (ADR-008).
- **Use several API keys.** Rejected: it breaks the free-tier constraint the user set and Groq's terms.

## Consequences
- A spent quota now costs seconds, not hours. Either the run continues on the fallback model, or the issue gets a clear "retry after ~N min".
- Results depend on which model actually ran. `fallback_calls` makes that visible, and the report must say so.
- Token use matters as an architecture input: on a free tier, the **daily quota limits how many issues we can run per day**, not only the per-minute rate. The builder's 165k tokens in run 10 was most of a day's quota. That is a reason to keep turns low (ADR-014).
- Tested with a fake client:
  - a 1200 s 429 on 120b falls back to 20b, and later calls go straight to 20b;
  - a 20 s 429 still sleeps and retries;
  - with both exhausted, it stops after 2 calls;
  - the judge stops without a fallback.
