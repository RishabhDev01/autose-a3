# ADR-008: The reviewer is isolated by job, model, prompt, inputs and permissions

## Status
Accepted (2026-11-21). Tested in experiment E1.

## Context
A reviewer that sees the implementer's reasoning tends to agree with it. LLMs also lean towards approving. The assignment requires that the reviewer sees only the issue, the diff and the repo at the PR head, and that it cannot push.

## Decision
The reviewer is isolated in five ways:

1. **Job.** It runs in a separate `review` job, on a fresh runner with a fresh checkout of the PR head SHA. No files from the build job are passed to it.
2. **Permissions.** `permissions: {contents: read, pull-requests: read}`. Its tools have no write function (ADR-005). Posting the review is done by a separate `post` job that contains no LLM.
3. **Inputs.** Issue text, `git diff origin/main...HEAD -- . ':!.autose'`, and repo read tools plus `run_tests`. It never sees spec, design or test report.
4. **Model.** A different family from the builder (ADR-006).
5. **Prompt.** An adversarial checklist. The reviewer must:
   - run the tests itself;
   - list at least two concrete risks or edge cases it tried;
   - map each claim in the issue to evidence in the diff;
   - output `approve` only if every issue requirement has evidence.

   Its output is JSON: `{"verdict", "target": "design|implement|null", "findings": [...]}`.

**Stopping it from approving everything.** We check calibration on 5 seeded PRs: 4 contain a known bug and 1 is correct. The approval rate on the buggy PRs is reported.

## Experiment E1
Reviewer on the same model as the builder vs. a different model, run on the 5 seeded PRs. We measure bugs caught and false alarms.

## Consequences
- The reviewer may miss intent that is only written in spec.md. That is deliberate: it judges against the issue, as a human maintainer would.
