# ADR-002: Control flow is a deterministic state machine in Python

## Status
Accepted (2026-11-21)

## Context
Someone must decide when a stage has passed, when to retry, and when to go back to an earlier stage. If an LLM planner makes these decisions, it can loop, skip checks, or declare success early. Free-tier models are also weaker at long-horizon planning. The assignment requires fixed stages and fixed checks anyway.

## Decision
- `autose/orchestrator.py` is a state machine: `SPEC → DESIGN → IMPLEMENT ⇄ TEST → RELEASE → REVIEW → DONE | STOPPED`.
- Transitions are decided by code, based on check results and counters:
  - Test failure: back to IMPLEMENT, at most 3 attempts.
  - After 3 failures: back to DESIGN once, with the failure log.
  - After that: STOPPED.
  - Reviewer verdict `changes` with target `design` or `implement`: re-enter that stage, at most 2 review rounds.
- Stages 1–5 run in one Actions job. The review runs in a second job (`needs: build`).
- A third job posts the review. If changes are requested, it re-dispatches the workflow with `workflow_dispatch` (inputs: issue, round, start stage).

## Options considered
- **LLM orchestrator with workers.** Rejected. It is not predictable or auditable, and it costs tokens.
- **Separate Actions jobs per stage, triggering each other.** Rejected. Each job would need its own checkout and environment setup, and passing artifacts between them is slow. We only split where isolation is needed (the reviewer).
- **Code state machine plus a job boundary for the reviewer (chosen).**

## Consequences
- Every transition is logged to `state.json` and the job summary, so a run can be followed on GitHub.
- Less flexible: the workflow cannot invent a new strategy. This is acceptable for small issues.
