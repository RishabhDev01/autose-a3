# ADR-012: A slim CI that the release stage starts with `workflow_dispatch`

## Status
Accepted (2026-11-21)

## Context
Stage 5's check is "the PR is open and CI passes". Reading the fork's inherited `.github/workflows/ci-workflow.yml` showed two problems:

1. **It cannot pass on our fork.** It runs a 17-job matrix (3 operating systems × 5 Pythons, plus PyPy) and uploads to Coveralls. Coveralls is not configured for the fork, so the upload and the `coveralls --finish` job fail. Each run would also cost about 17 runner-jobs.
2. **It would never start.** Our release stage opens the PR with the job's `GITHUB_TOKEN`. GitHub does not trigger `pull_request` or `push` workflows from events caused by `GITHUB_TOKEN`, to prevent recursive runs. `workflow_dispatch` and `repository_dispatch` are the documented exceptions.

## Decision
- Replace the CI with: `ubuntu-latest`, Python 3.12 and 3.13, `pytest -q`, `permissions: contents: read`, `timeout-minutes: 10`.
- Triggers: `push` to master, `pull_request` to master (for human PRs), and `workflow_dispatch`.
- The release stage runs `gh workflow run ci-workflow.yml --ref autose/issue-N`, finds the run for the head SHA, and waits with `gh run watch --exit-status`. The run URL is written into `pr.md`.

## Options considered
- **Keep upstream CI.** Rejected. It always fails (Coveralls) and is slow.
- **Use a personal access token (PAT) so PR events trigger CI.** Rejected. It adds a long-lived secret with wide scope, and it makes the bot act as a person (ADR-009).
- **Run the tests inside the build job only.** Rejected. Stage 4 already does this. CI is meant to be a **separate** clean-environment check.
- **Slim CI plus `workflow_dispatch` (chosen).**

## Consequences
- CI checks two Python versions instead of five, and Linux only. This is a threat to validity for OS-specific bugs, such as Windows file handling in `JSONStorage`.
- mypy and pycodestyle are not run in CI. The reviewer can still run them.
