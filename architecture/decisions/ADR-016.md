# ADR-016: The builder patches what the orchestrator finds (localize → patch → validate)

## Status
Accepted (2026-11-22). Amends [ADR-005](ADR-005.md) and [ADR-014](ADR-014.md) for stages 3–4, based on run 12.

## Context: what runs 10 and 12 showed
Both runs passed spec and design, then failed in the builder's free tool loop (ADR-005): 40 turns, then `AgentStopped: max_turns`.

| | Run 10 (gpt-oss-120b) | Run 12 (gpt-oss-20b via ADR-015) |
|---|---|---|
| Spec / design | ✔ / ✔ | ✔ / ✔ (design: `Table._update_table`) |
| Builder turns | 40, no finish | 40, no finish |
| What it did | 13 bad-argument reads, 9 failed `edit_file` | read `_update_table` **4 times**, `conftest.py` twice, rewrote its test file 3 times, never ran the full suite |
| Builder tokens | 165k | 179k (≈ 4.5k per turn) |

ADR-014 fixed the tool *arguments*, and run 12 then shows the deeper problem:
- The model **spends its turns finding code**, not changing it.
- Context compaction (ADR-013) drops what it read, so it reads again.

Under the free tier this cannot work:
- 8k tokens per minute means almost every turn waits on a 429.
- The **daily** quota refills at about 200k / 24 h ≈ **8k tokens per hour per model**. We derived this from run 12's message: "Used 197443, Requested 4592, try again in 880 s".
- So one 180k-token builder attempt uses about a day of quota. Five issues plus two experiments are out of reach.

The finding step does not need an LLM at all: the design already names the file and the function (and stage 2 checks that they exist).

## Decision
Split stages 3–4 into three parts. Only the middle part uses the model.

1. **Localize (code, no LLM).**
   - For each design row under `tinydb/`, `ast` extracts the named definition.
   - It adds up to 3 short helpers (80 lines or fewer) that the definition calls.
   - For a NEW method it extracts the class outline.
   - Total: 9,000 characters or less.
2. **Patch (one LLM call).**
   - The builder gets the ACs, the design approach and that code. It has no tools.
   - It answers in a fixed text format:
     - `### REPLACE <path> <Name>` (or `### ADD <path> <Class|MODULE>`) followed by a complete definition;
     - `### TESTS` followed by the complete new file `tests/test_autose_issue_N.py`;
     - `### SUMMARY`.
3. **Validate (code).**
   - The orchestrator replaces each definition **by name** and re-indents it.
   - It refuses paths outside `tinydb/*.py`, unknown names and syntax errors, each before writing.
   - It writes the test file and runs the unchanged ADR-007 checks (build, full suite, baseline count, AC → test map).
   - On failure, the check message and the **current** code (including the model's earlier edits) go back for another attempt.
   - At most 3 attempts, then a design re-entry (ADR-002), as before.

Two related changes:
- A run stopped by `QuotaExhausted` (ADR-015) **resumes at that stage** on the next `/autose`, and an attempt is counted only once the model has answered.
- A fresh restart **resets `tinydb/`, `tests/` and `docs/` to master**. Run 12 had left a half-written test file on the branch.

`BUILDER_MODE=agent` keeps the old tool loop, for comparison.

## Options considered
- **Keep the tool loop and raise `max_turns`.** Rejected: more turns means more tokens, and quota is the binding constraint.
- **Give the tool loop the localized code up front.** Rejected: it would still re-send the growing history every turn. One answer per attempt is the cheapest shape.
- **Ask for a unified diff.** Rejected: models get hunk headers and context lines wrong, the same failure as `edit_file` in run 10. Replacing a whole definition by name has nothing to mismatch.
- **JSON output with code in strings.** Rejected: escaping errors, and Groq's `output_parse_failed` (run 9) is more likely with long JSON.

## Consequences
- **Cost.** About 2.5k prompt tokens per attempt (largest seen in the local test: 8,080 characters including the prompt), against about 180k per attempt before. A whole issue now fits in about an hour of refilled quota.
- **Scope is limited to what the design names.** If the fix is elsewhere, the checks fail and the design re-entry (ADR-002) asks the planner to name the right place. This makes the **design stage carry more weight**, which is a trade-off for the report.
- **Tests go in a new file** per issue rather than appended to existing files. This is easier for the reviewer to read; the downside is the file is not grouped by module.
- This is the "agentless" pattern (localize → repair → validate). With a small model and a small context, **fixed control flow beats a free agent loop**: the same deterministic-orchestrator argument as ADR-002, applied inside a stage.
- **Tested locally.** On issue #3's real spec and design, with a scripted model:
  1. a malformed answer is rejected with a format message;
  2. a wrong test fails the real suite, and the failure is fed back;
  3. a correct answer passes every check (227 + 4 tests).
  
  Also tested: ADD to a class, re-ADD replacing instead of duplicating, blocked paths (`.github/`, `autose/`, `tinydb/../`), syntax errors, and a quota stop resuming at `implement`.
