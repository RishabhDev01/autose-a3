# ADR-023: Builder output limit sized for Gemini thinking; cut-off answers reported as such

## Status
Accepted (2026-11-22). Amends [ADR-016](ADR-016.md) (patch-mode builder) and [ADR-022](ADR-022.md).

## Context
Run [44990995937](https://github.com/RishabhDev01/tinydb/actions/runs/44990995937) (run 21, issue #4, string doc IDs) resumed at design. Design passed with 4 rows: `Table.get`, `Table.remove` and `Table.update`, plus tests. The patch builder then failed 3 attempts, went back to design, and failed 3 more.

- The six builder calls produced **17,966 completion tokens**, about **2,994 per call**, against `max_tokens=3000`. Every answer was cut off at the limit.
- **Gemini counts its thinking tokens as output** (ADR-021 already noted this for the reviewer).
- Issue #3 needed one small function, and its single call fit in about 3k. Issue #4 needs three larger functions plus five tests.
- **Three attempts failed as format errors**: "no `### REPLACE` block found" and "`### REPLACE … Table.remove` has no python code block". Those were really cut-off answers, but the builder was told it had used the wrong format.
- **The other attempts had failing tests.** Those failures went into the redesign feedback. The planner then concluded that "doc IDs in storage are strings" and redesigned `remove` and `update` around `str(doc_id)`. That cannot work, because `_update_table` gives the updater **int** keys. **A truncation fault in stage 3 led to a wrong design in stage 2.**

## Decision
- **Builder `max_tokens` 3000 → 12000.** It can be set with the `BUILDER_MAX_TOKENS` repository variable. At $3.75 per 1M output tokens, a full 12k answer costs about $0.045.
- **A cut-off is detected and named.** `llm.chat` records each role's `finish_reason`. A reply that ends with `"length"` is logged and counted in `USAGE[role]["truncated"]`.
  - If such a reply cannot be parsed, the builder is told: "YOUR ANSWER WAS CUT OFF at the output limit … answer again, shorter: replace only the definitions that must change…"
  - The generic format error is no longer used for this case, so the feedback describes the real cause.
- **Builder budget 120k → 200k,** so six longer attempts still fit.
- **A restart at `spec` or `design` resets the code and the counters,** as a restart at `guard` already did (ADR-016/017).
  - It resets `tinydb/`, `tests/` and `docs/` to master and sets the attempt counters and design re-entries to 0. The spec in `.autose/` is kept.
  - Without this, re-running issue #4 at design would have inherited attempts 3/3, re-entries 1/1 and run 21's edits, and the builder would have stopped at once. This was found before re-running, by reading `setup()`.

## Options considered
- **Lower reasoning effort to none for the builder.** This saves output tokens, but thinking helps the one-shot patch get the code right.
- **Ask for unified diffs instead of whole definitions.** Shorter, but diffs written by a model often do not apply, which is why ADR-016 replaces definitions by name.
- **Split the answer into one call per definition.** More calls, and the tests would have to be written separately; kept as a later option if 12k is still not enough.

## Consequences
- **The truncation counter is evidence for the report:** USAGE shows how often each role hit its limit.
- **A wrong design written from misleading feedback stays a risk.** The design check does not test the planner's claims about the code. This is noted for the report as a limitation of the stage-3 → stage-2 loop.
- **Tested** with a mocked client: `finish_reason` "length" vs "stop" is recorded; `max_tokens` 12000 is sent; `truncated` is counted; budgets are planner 400k and builder 200k. The TinyDB suite passes (228).
