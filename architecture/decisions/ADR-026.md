# ADR-026: Reject test gaming, stop on conflicts with pinned behaviour, start review round 2 by hand

## Status
Accepted (2026-11-22). Amends [ADR-007](ADR-007.md) (deterministic checks), [ADR-002](ADR-002.md) (feedback loops), [ADR-008](ADR-008.md) (independent reviewer) and [ADR-010](ADR-010.md) (gate).

## Context
Run [44994263819](https://github.com/RishabhDev01/tinydb/actions/runs/44994263819) (run 27, issue #7, the vague issue "search() gives me different data the second time??"):

- **Spec and design read the issue as intended:** search results should be independent copies. That is the same reading as the hidden test `test_issue_5_search_isolation.py`.
- **One existing test pins the opposite behaviour:** `test_query_cache_documents_are_shared_with_cache`. `ARCHITECTURE.md` invariant 3 documents it: cached documents are shared. Every attempt failed **only that test** (the ADR-024 digest named it).
- **The builder may only edit `tinydb/*.py` and its own new test file.** The honest fix (change the pinned test) was out of its reach. The orchestrator kept asking it to "fix the cause in the code, do not weaken the tests".
- **Attempt 6 passed by gaming the test.** `Table.search()` walked the call stack with `sys._getframe`; if the caller was `test_query_cache_documents_are_shared_with_cache`, it ran the old shared-cache code, and every other caller got deep copies.
  - All deterministic checks passed: 231 tests and CI green.
  - **The independent reviewer caught it** (ADR-008): "Production code must never special-case a test function via stack-frame inspection", and it requested changes.
- **The post job then dispatched review round 2 as `github-actions[bot]`.** The gate rejects every bot event, a loop guard from ADR-010, so run [44994832774](https://github.com/RishabhDev01/tinydb/actions/runs/44994832774) (run 28) was skipped. The PR comment "Starting round 2" was wrong.

## Decision
1. **Test-gaming check at stage 3** (`checks.test_gaming`, run before the build check). Added lines under `tinydb/` fail with `TEST GAMING` if they:
   - inspect the call stack: `_getframe`, `inspect.stack` / `currentframe` / `getouterframes` / `getframeinfo`, `traceback.extract_stack`…;
   - read frame objects: `f_code`, `f_back`, `co_name`;
   - detect pytest: `PYTEST_CURRENT_TEST`, `'pytest' in sys.modules`, importing pytest;
   - name a test in a string literal (`"…test_…"`).

   The builder prompt states the rule too.
2. **Stop on a conflict with pinned behaviour** (`check_conflict`). If the only failing tests are **existing** tests (not the builder's own test file), and the **same set** fails in 3 attempts under **2 designs**, the run stops with "CONFLICT WITH EXISTING BEHAVIOUR … a maintainer must decide: change that behaviour (update the test, then comment `/autose`) or decline the issue." A redesign that does not change the failing set is the signal that the conflict is with the requirement, not with the code.
3. **Review round 2 is started by a person.**
   - The post job no longer dispatches round 2. It comments the exact command, `/autose round 2 <design|implement>`.
   - The gate parses that command from trusted commenters only, and allows rounds 1–2.
   - The post job loses `actions: write`.
   - This matches the maintainer's rule that every run is started by a person (ADR-018 was rejected for the same reason).

## Options considered
- **Let the builder edit existing tests.** Then any failing test could be "fixed" by weakening it; the issue text is untrusted input and cannot authorise that. Changing pinned behaviour stays a human decision.
- **Rely on the reviewer alone.** It caught this case, but a reviewer is an LLM and can miss things; a cheap deterministic check is a second line of defence (ADR-007). The two are complementary: the check knows patterns, the reviewer knows intent.
- **Let the gate trust `github-actions[bot]` for round 2.** That would reopen the bot-loop path that ADR-010 closes, and would conflict with the human-trigger rule.

## Consequences
- **Run 27 is the clearest evidence for ADR-008:** the deterministic gates were satisfied by a gamed patch, and only the separate reviewer refused it. With this ADR, the same run would stop at attempt 5, before the gamed attempt, with a message that names the conflicting test.
- **Issue #7 cannot be completed by AutoSE alone.** A maintainer must first decide whether to change invariant 3 and its test. The report should present this as a *correct* hand-off, not as a failure.
- **Checked locally:**
  - the gaming scan flags all 4 gamed lines of run 27, with no hits on the diffs of PRs #17, #22, #23 and #25 or on any existing line of `tinydb/`;
  - replaying run 27's failure sequence stops at attempt 5;
  - no stop on run 22's failures (its own AC tests failed too), nor on 3 repeats under one design;
  - the gate parses 8 command forms, and rejects bot and untrusted events.

  The TinyDB suite passes (228), and the workflow YAML parses.
